**วันที่ปรับปรุง:** 27 กรกฎาคม 2026  
**สถานะโครงการ:** Basic Combat ทำงานแล้ว และกำลังเข้าสู่ Visual Combat Prototype

> เอกสารนี้เป็นภาคปรับปรุงอย่างเป็นทางการของแผนฉบับ 0.1 โดยให้ถือข้อความในเอกสารนี้แทนส่วนที่ขัดแย้งกัน โดยเฉพาะหัวข้องานภาพ ขอบเขต Prototype, Roadmap, งานถัดไป และกฎการทำงาน

# 1. เหตุผลที่ต้องปรับแผน

Combat Prototype ปัจจุบันสามารถกดโจมตี ตั้งรับ ลด HP จบการต่อสู้ และเริ่มใหม่ได้แล้ว แต่หน้าจอยังประกอบด้วยข้อความ ปุ่ม และ Combat Log เป็นหลัก จึงมีลักษณะเหมือนแบบฝึกเขียนโปรแกรมมากกว่าเกม

แนวทางเดิมที่รอให้ระบบต่อสู้และ NPC AI สมบูรณ์ก่อนเริ่มทำภาพมีความเสี่ยงดังนี้:

- ผู้พัฒนาไม่เห็นภาพปลายทางของเกม
- ไม่สามารถทดสอบอารมณ์และการอ่านฉากต่อสู้ได้
- การจัดตำแหน่งตัวละครและ UI อาจต้องรื้อภายหลัง
- Prototype ขาดแรงจูงใจในการพัฒนาต่อ
- ระบบที่ทำงานได้อาจยังไม่รู้สึกสนุกเมื่อไม่มี Visual Feedback

ดังนั้นโครงการจะเปลี่ยนเป็นแนวทาง:

> **พิสูจน์ระบบขั้นต่ำก่อน แล้วพัฒนาภาพและระบบควบคู่กัน**

---

# 2. หลักการพัฒนาใหม่

Prototype ของเกมต้องพิสูจน์พร้อมกันสองด้าน

## 2.1 Functional Prototype

ระบบตอบสนองได้จริง เช่น:

- กดโจมตีแล้วเกิด Damage
- กดตั้งรับแล้วลด Damage
- HP ลดลงถูกต้อง
- มีสถานะชนะและแพ้
- เริ่มการต่อสู้ใหม่ได้

## 2.2 Visual Prototype

หน้าจอต้องเริ่มสื่อภาพของเกมจริง เช่น:

- มีฉากหลัง
- มี Player, NPC และ Enemy อยู่บนสนาม
- มองออกว่าใครเป็นฝ่ายใด
- มี HP Bar
- เห็นว่าใครโจมตีใคร
- มี Feedback เมื่อเกิด Damage
- แผงคำสั่งดูเป็น UI ของเกม ไม่ใช่หน้า Debug

## 2.3 กติกาการทำงาน

- สร้างระบบขั้นต่ำให้กดแล้วเกิดผลก่อน
- หลังระบบพื้นฐานหนึ่งวงจรทำงาน ให้เพิ่มภาพชั่วคราวทันที
- ภาพชั่วคราวต้องดูเป็นเกม แม้ยังไม่ใช่งาน Final
- ไม่รอให้ NPC AI, Injury, Permadeath และ Journey เสร็จก่อนเริ่มทำภาพ
- ไม่ผลิต Sprite Sheet จำนวนมากจนกว่าสไตล์และขนาดตัวละครจะผ่านการทดสอบ
- ใช้ AI เพื่อช่วยสร้าง Concept และ Reference
- ใช้ Pixelorama ทำ Asset ที่ต้องคงสัดส่วนและนำเข้าเกมจริง

# 3. เป้าหมาย Visual Combat Prototype

เปลี่ยนหน้าจอปัจจุบันให้เป็นฉากต่อสู้ด้านข้างแบบปาร์ตี้

```text
┌────────────────────────────────────────────────────────────┐
│            ฉากป่ารกร้าง / ซากถนนโลกเก่า                  │
│                                                            │
│ Player   NPC A   NPC B   NPC C       Enemy A   Enemy B     │
│   HP       HP      HP      HP           HP        HP       │
│                                                            │
├────────────────────────────────────────────────────────────┤
│ Combat Log แบบกระชับ                                       │
├────────────────────────────────────────────────────────────┤
│ [โจมตี] [ตั้งรับ] [ช่วยเหลือ] [ชี้นำ] [ถอย]               │
└────────────────────────────────────────────────────────────┘
```

Visual Prototype ถือว่าผ่าน เมื่อผู้ที่เห็นหน้าจอสามารถบอกได้ทันทีว่าเป็นเกมต่อสู้แบบปาร์ตี้ ไม่ใช่หน้าทดลอง UI

---

# 4. Asset ที่ต้องมีในรอบนี้

สร้างเพียง Asset ขั้นต่ำดังนี้:

## 4.1 ฉาก

- ฉากหลัง Pixel Art 1 ฉาก
- ธีมชั่วคราว: ป่ารกร้างที่มีซากถนนหรือโครงสร้างโลกเก่า
- มีพื้นยืนชัดเจนสำหรับตัวละคร
- รายละเอียดไม่มากจนแย่งสายตาจากตัวละครและ UI

## 4.2 ฝ่ายผู้เล่น

- Player: เสื้อโทนน้ำเงิน ถือดาบ
- NPC A: เสื้อเขียว ถือธนู
- NPC B: เสื้อครีม ถือกระเป๋ายาหรือไม้เท้า
- NPC C: เสื้อแดง ถือหอก

## 4.3 ฝ่ายศัตรู

- Enemy A: สัตว์ป่ากลายพันธุ์
- Enemy B: โจรหรือมนุษย์สวมหน้ากาก

## 4.4 UI

- HP Bar ของแต่ละตัว
- ชื่อหรือสัญลักษณ์แยกตัวละคร
- แผงคำสั่งด้านล่าง
- Combat Log แบบกระชับ
- ตัวเลข Damage ลอยขึ้น

Asset ทั้งหมดเป็น Placeholder ได้ แต่ห้ามใช้ Label หรือสี่เหลี่ยมเปล่าแทนตัวละครเป็นภาพนำเสนอหลักหลัง Milestone 1

---

# 5. ขนาดและ Animation ขั้นต่ำ

## 5.1 ขนาด Sprite

- ความสูงตัวละครชั่วคราวประมาณ 24–32 พิกเซล
- ใช้ Pixel Art รายละเอียดน้อย
- Silhouette ชัด
- จำกัด Palette
- ใช้สีและอาวุธช่วยแยกตัวละคร

## 5.2 Pose ขั้นต่ำ

ตัวละครหนึ่งตัวใช้เพียง:

- Idle 1 เฟรม
- Attack Pose 1 เฟรม
- Hurt 1 เฟรม
- Down 1 เฟรม

ยังไม่สร้าง Sprite Sheet 8 เฟรม และไม่ต้องทำ Animation ครบทุกตัวก่อนนำเข้าเกม

## 5.3 Visual Feedback ใน Godot

ใช้ระบบใน Godot ช่วยเพิ่มความรู้สึกแทนการวาดหลายเฟรม:

- Tween ให้ตัวละครพุ่งเข้าหาเป้าหมาย
- Hit flash เมื่อได้รับความเสียหาย
- ตัวละครสั่นหรือถอยหลัง
- Floating Damage
- HP Bar ลดลงแบบเคลื่อนไหว
- Slash Effect ขนาดเล็ก
- เปลี่ยนเป็น Down Pose เมื่อ HP หมด

---

# 6. การใช้ AI และ Pixelorama

## 6.1 AI ใช้สำหรับ

- Concept ตัวละคร
- Reference ของชุดและอาวุธ
- Mood และ Color Palette
- Monster Concept
- ฉากหลังต้นแบบ
- UI Reference

## 6.2 AI ไม่ใช้เป็นตัวหลักสำหรับ

- Sprite Sheet ขั้นสุดท้าย
- Animation หลายเฟรม
- Asset ที่ต้องคงสัดส่วนข้ามตัวละคร
- Asset Production จำนวนมาก

## 6.3 Workflow

1. ใช้ AI สร้างแนวคิดหรือ Reference
2. เลือก Silhouette และ Palette
3. ลดรูปใน Pixelorama
4. Export เป็น PNG
5. Import เข้า Godot โดยปิด Texture Filter หรือใช้ Nearest
6. ทดลองในฉากจริงก่อนเพิ่มรายละเอียด

# 7. Roadmap ฉบับปรับปรุง

## Milestone 0 — Project Setup — เสร็จแล้ว

- สร้างโปรเจกต์ Godot
- ตั้ง Renderer เป็น Compatibility
- ตั้ง Git
- สร้างฉาก `combat_prototype.tscn`
- ตั้งหน้าจอ 1280 × 720

## Milestone 1 — Basic Combat — เสร็จขั้นพื้นฐานแล้ว

- Player HP
- Enemy HP
- Attack
- Defend
- Damage
- Win / Lose
- Restart
- Combat Log

## Milestone 1.5 — Visual Combat Prototype — งานถัดไป

- ปรับ Layout เป็นสนามต่อสู้ด้านข้าง
- เพิ่มฉากหลัง 1 ฉาก
- เพิ่ม Player 1 ตัว
- เพิ่ม NPC 3 ตัว
- เพิ่ม Enemy 2 ตัว
- เปลี่ยน HP Label เป็น HP Bar
- ปรับแผงคำสั่ง
- เพิ่ม Tween การโจมตี
- เพิ่ม Hit flash
- เพิ่ม Floating Damage
- เพิ่ม Down Pose

เป้าหมายของ Milestone 1.5 คือเปลี่ยนหน้าทดลองระบบให้เริ่มมีภาพและความรู้สึกเหมือนเกมจริง ก่อนเพิ่มความซับซ้อนของ NPC AI

## Milestone 2 — Party and NPC AI

- เชื่อม NPC 3 คนเข้าสู่การต่อสู้จริง
- เชื่อม Enemy 2 คนเข้าสู่การต่อสู้จริง
- Speed Order
- NPC เลือก Action
- แสดง Action ผ่าน Sprite
- แสดงเหตุผลการตัดสินใจ

## Milestone 3 — Guidance

- คำชี้นำ 4 แบบ
- NPC ทำตามหรือต่อต้าน
- Trust และ Discipline
- Feedback ที่เข้าใจได้

## Milestone 4 — Down, Help, Death, Retreat

- Down
- Bleed-out Timer
- Help
- Retreat
- Death
- NPC ช่วยหรือหนี
- สรุปผู้รอดชีวิต

## Milestone 5 เป็นต้นไป

ดำเนินตามแผนฉบับ 0.1 ในหัวข้อ Journey Prototype, Town Loop และ Vertical Slice

# 10. ความเสี่ยงที่เพิ่มเข้ามา

## Prototype ดูเป็นแบบฝึกเขียนโปรแกรมจนหมดแรงจูงใจ

แนวทางแก้:

- จำกัดระยะเวลาที่ใช้ Label และสี่เหลี่ยมล้วน
- เพิ่ม Visual Prototype หลัง Basic Combat ทำงานทันที
- ทำฉาก ตัวละคร และ Feedback จำนวนน้อยก่อน
- ใช้ภาพชั่วคราวที่มี Silhouette และสีแยกตัวละครชัด
- ตรวจความรู้สึกจากภาพหน้าจอเป็นระยะ ไม่ตรวจเฉพาะโค้ด
- แยกงานภาพชั่วคราวเพื่อสร้างแรงจูงใจออกจากงานภาพ Final

# 11. กฎการทำงานฉบับปรับปรุง

1. พิสูจน์ระบบขั้นต่ำก่อนผลิต Asset จำนวนมาก
2. หลังระบบพื้นฐานทำงาน ให้พัฒนาภาพและระบบควบคู่กัน
3. Placeholder ต้องสื่อรูปร่าง ตัวละคร และบรรยากาศของเกมได้
4. Prototype มาก่อนเกมเต็ม
5. ไม่เพิ่มระบบใหม่ก่อน Milestone ปัจจุบันเล่นและมองเห็นผลได้
6. ไม่สร้าง Sprite Sheet จำนวนมากก่อนล็อกขนาดและสไตล์
7. Commit Git ทุกครั้งที่จบงานสำคัญ
8. ทำทีละ Milestone และต้องมีภาพผลลัพธ์ที่ตรวจสอบได้
9. Feature ใหม่ต้องเพิ่มความสนุกหรือความชัดเจนของแกนหลัก
10. สิ่งที่ไม่จำเป็นต่อ Prototype ให้ย้ายไป Backlog
11. ทดสอบผู้เล่นก่อนลงทุนกับงานภาพ Final ไม่ใช่ก่อนทำภาพทุกชนิด
12. ความสำเร็จระยะแรกคือ “เล่นได้ เข้าใจได้ และเริ่มรู้สึกเหมือนเกม” ไม่ใช่ “ระบบครบแต่ไม่มีภาพ” หรือ “ภาพสวยแต่ระบบไม่ทำงาน”
