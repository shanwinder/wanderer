# 1. ผลกระทบต่อแกนเกมเดิม

| แกน Wanderer เดิม | สิ่งที่ต้องรักษา | การเชื่อมพลังใหม่ |
|---|---|---|
| 2D party-based RPG, side-view | ฉากต่อสู้/รูปแบบทีมเดิม | เพิ่มสถานะเฉพาะเมื่อมีอุปกรณ์ |
| Player 1 + NPC 3 | ผู้เล่นควบคุมเฉพาะตนเอง | ไอเทมไม่ได้ทำให้สั่ง NPC โดยตรง |
| Guidance, Discipline, Trust | NPC อาจทำตาม/ปฏิเสธพร้อมเหตุผล | NPC ประเมินความเสี่ยงใช้แร่เอง |
| Injuries, Down, Death, Retreat | ความตายมีผลและต้องเจ็บจริง | พลังช่วยลด/ชะลอ ไม่ลบกติกาตาย |
| Progress from use, no starting Class | ผู้เล่นค่อย ๆ ได้บทบาทจากการกระทำ | เพิ่มความชำนาญพ้องพลังเป็น specialization ภายหลัง |
| Town → Quest → Journey → Combat | เปิดเส้นทางโลกเก่าเป็นแกนหลัก | บางเควสมีเบาะแส/อุปกรณ์พิเศษ |
| Low-budget solo + learn by doing | หนึ่งแนวคิดต่อรอบ เรียน Godot จริง | เริ่มจาก effect หนึ่งชิ้น ไม่สร้าง framework ใหญ่ |
| Premium, offline, no gacha | ไม่มีขาย power/การคืนชีพ | อุปกรณ์ได้จากการเล่น ไม่ใช่ระบบเงินสด |

**สิ่งที่ไม่เปลี่ยน:** ขอบเขต Milestone 1.5B, 1.5C, 1.5D ที่เอกสาร v0.3 ระบุ, ลำดับ Milestone 2–7, นิยาม prototype ของ v0.1 และเป้าหมายเรียนรู้ของ v0.4

# 2. Design Pillars ของกลไกดาราศิลา

1. **Visible but uncommon** — มีหลักฐานว่าพลังมีจริง แต่ปกติไม่เจอผลึก/ผู้ใช้พลังทุก encounter
2. **Item-gated** — สกิลพิเศษไม่เกิดหากไม่สวม/ถืออุปกรณ์ที่มีแกนดาราศิลา
3. **Context-sensitive** — มีประโยชน์เป็นบางสถานการณ์ ไม่ใช่ power creep ที่แทนการโจมตีปกติ
4. **Costly** — จ่ายด้วยความเสี่ยง fatigue/strain, charge/heat, durability หรือ opportunity cost
5. **Learnable** — มีคำเตือนสภาพเครื่องมือก่อนผลเสียที่รุนแรง
6. **Autonomous companions** — NPC ตัดสินใจใช้/เก็บ/ปฏิเสธเองด้วยเหตุผล
7. **Lore-consistent** — พลังจากวัสดุจริง ไม่ใช่มนต์ใด ๆ ที่ไม่มีตัวกลาง
8. **Prototype-first** — implement ทีละความสามารถ ทดสอบความสนุกก่อนทำ art, balance, world scale

# 3. โมเดลระบบเชิงแนวคิด

แยก 5 ส่วนเพื่อให้ Godot พัฒนาได้ทีละชั้น โดย **ยังไม่ต้องสร้าง class ทุกตัวทันที**:

1. **Item Definition:** ชื่อ, ชนิด, equipment slot, effect id, limit, เวลาเตรียม, ค่าบำรุง
2. **Crystal Condition:** Quality, Integrity, Stress, Stability (เชิงข้อมูล; เฉพาะบางค่าต้องใช้ในต้นแบบ)
3. **User State:** Resonance Proficiency, Strain, Wound, Fatigue
4. **Action Context:** ผู้ใช้, เป้าหมาย, ระยะ/แถว, เป้าหมายอ่อนแรงหรือเลือดไหล, guidance, ตัวเลือกถอย
5. **Decision & Feedback:** Action/Refusal + Reason Code + ผลและสัญญาณความเสี่ยง

ใน Prototype เล็กที่สุด ใช้เพียง equipped (true/false), available (true/false), user strain, และคำอธิบายผล; data อื่นเป็นอนาคต

## 3.1 ลำดับตรวจสอบการใช้ไอเทม

~~~text
ผู้ใช้ตัดสินใจจะใช้อุปกรณ์
  → ตรวจว่าเป็นเจ้าของ/ถือ/สวมและอุปกรณ์ทำงานได้
  → ตรวจเงื่อนไขเป้าหมาย ตำแหน่ง เวลา และอาการบาดเจ็บ
  → แสดงคาดการณ์ผล ประโยชน์และความเสี่ยงที่รู้ได้
  → ผู้ใช้ยืนยันเอง หรือ NPC AI ตัดสินใจ
  → หัก cost/เพิ่ม strain/stress
  → ประมวลผลสำเร็จ/สำเร็จบางส่วน/ล้มเหลวที่อธิบายได้
  → แสดง VFX, log, condition และผลต่อบาดแผล
  → บันทึกข้อมูลต่อเนื่องตามกติกา save
~~~

ห้ามปล่อย effect ก่อนยืนยันต้นทุนและความถูกต้องของเป้าหมาย; ห้ามสุ่มผลร้ายแบบไม่ให้สัญญาณเตือน

## 3.2 สถานะไอเทม

| สถานะ | ความหมาย | กระทำได้หรือไม่ |
|---|---|---|
| Ready | ติดตั้งและพร้อมกระตุ้น | ได้ |
| Recovering | ระยะพักหรือเย็นตัว | ยังไม่ได้ |
| Warning | ใช้ได้แต่ความเสี่ยงสูงขึ้น | ได้เมื่อมีคำเตือน |
| Overstrained | ภาวะไม่เสถียร มีความเสี่ยงชัด | ถูกจำกัดตามชนิดอุปกรณ์ |
| Broken | ผลึก/โครงเสียหายรุนแรง | ไม่ได้จนผ่านขั้นตอนซ่อมที่ออกแบบ |

*สำหรับต้นแบบแรก* ใช้เพียง Ready / Spent ไม่ต้อง implement state machine เต็ม

# 4. ต้นแบบขั้นต่ำ (Minimum Resonance Experiment — MRE-1)

**แนะนำอุปกรณ์แรก:** จี้ชีพจร (Pulse Pendant) เพราะเชื่อมกับ NPC Compassion, Help, Down และการเลือกช่วยใครอย่างตรงแกนเกม; แต่ต้องรอให้ Milestone 2–4 พื้นฐานทำงานก่อน ไม่แทรกก่อนหน้า

## 4.1 สมมติฐานที่ต้องพิสูจน์

> “การมีอุปกรณ์ช่วยประคองชีวิตหายากหนึ่งชิ้น ทำให้การตัดสินใจช่วยคนของ NPC น่าสนใจขึ้น โดยไม่รู้สึกว่าเกมโกงและไม่ลบความหมายของการบาดเจ็บหรือความตาย”

## 4.2 Scope ใน MRE-1 — ต้องมี

- ชุดตัวละคร Player + NPC 3 + ศัตรูตาม prototype ที่พัฒนาถึงตอนนั้น
- ผู้ถืออุปกรณ์ 1 คน (ทดสอบ Player และ NPC ใน scenario ต่างกัน)
- อุปกรณ์เพียงหนึ่งชนิด มี **การใช้งานปลอดภัย 1 ครั้งต่อการต่อสู้** เป็นตัวเลขชั่วคราว *เพื่อทดสอบเท่านั้น*; หลังจากนั้นเป็น Spent
- ใช้กับตัวละคร Alive/Down ที่ยังอยู่ในหน้าต่างช่วยเหลือเท่านั้น (กฎเป้าหมายตามการทดสอบ Injury)
- ถ้าไม่มีผู้บาดเจ็บที่เข้าเงื่อนไข ตัวเลือกไม่พร้อมใช้งาน พร้อมคำอธิบาย
- ผลทดสอบ: ชะลอ bleed-out หรือเสถียรอาการหนึ่งระดับ; **ไม่คืนชีพ Dead**
- NPC มีเหตุผลสำหรับใช้งาน/ไม่ใช้งาน, Log อ่านได้
- หลังใช้เกิดภาพและเสียงสั้น ๆ ใช้ Placeholder ได้
- เริ่ม encounter ใหม่ reset เฉพาะต้นแบบ; ยังไม่ทำ durability persistent หากระบบ save ไม่พร้อม

## 4.3 Scope ใน MRE-1 — ห้ามทำ

- หลายสี/หลายเกรดแร่, ไอเทมคราฟต์เอง, forging minigame, skill tree Resonance, RNG world drops, mining, NPC ช่างสิบแบบ
- เมือง/เควสใหม่เพื่ออธิบายอุปกรณ์โดยเฉพาะ
- โหมด multiplayer หรือ backend
- ระบบการคืนชีพ, จิตวิญญาณ, การย้อนเวลา
- Particle แสงไฟจำนวนมากที่บังการตัดสินใจ

## 4.4 Acceptance Criteria

1. ไม่มีอุปกรณ์ → ไม่ปรากฏคำสั่ง Resonance/ใช้ไม่ได้และไม่หัก cost
2. Equip อุปกรณ์ถูกต้อง → มีตัวเลือกเมื่อเป้าหมายเข้าเงื่อนไข
3. Use สำเร็จหนึ่งครั้ง → ผู้ใช้/เป้าหมายเปลี่ยนสถานะถูกต้อง และอุปกรณ์เป็น Spent
4. ใช้ซ้ำหลัง Spent → ปฏิเสธอย่างปลอดภัย ไม่มีผลซ้ำและไม่มีต้นทุนซ้ำ
5. เลือก Dead เป็นเป้าหมาย → ไม่มีผลคืนชีพ และ UI บอกเหตุผล
6. NPC ถืออุปกรณ์ → พิจารณา Help vs Attack vs Defend vs Retreat ได้ ไม่จำเป็นต้องใช้เสมอ
7. Guidance ขัดกับสถานการณ์ → NPC อาจปฏิเสธและบอกเหตุผล ไม่ลบ autonomy
8. Combat จบ → ชนะ/แพ้/ถอยทำงานเหมือนเดิม ไม่มี softlock
9. ผู้เล่นมองออกใน 1–2 รอบว่าใครใช้อุปกรณ์และผลที่เกิดกับใคร
10. Tests/คู่มือเล่นยืนยันว่าไม่มีการชุบตายด้วยไอเทมนี้

# 5. การทดสอบ NPC Decision ให้ยุติธรรม

## 5.1 Inputs ขั้นต่ำในอนาคต

- มีอุปกรณ์ไหมและพร้อมใช้หรือไม่
- อาการบาดเจ็บของตัวเอง/สมาชิกทุกคน
- Compassion, Courage, Discipline, Trust ตาม milestone ที่ใช้งานแล้ว
- เหตุผลด้านความปลอดภัย: ถ้าตัวเองกำลังจะล้ม การช่วยคนอื่นมีความเสี่ยงหรือไม่
- Guidance จาก Player เป็น *น้ำหนัก* ไม่ใช่คำสั่งที่ตัดสินผลเด็ดขาด

## 5.2 Reason Codes สำหรับ Debug และ UI

| Code | ความหมายผู้เล่น | การตรวจสอบ |
|---|---|---|
| HELP_BLEEDING_ALLY | ช่วยเพื่อนที่เสียเลือด | มี target Alive/Down และช่วยได้ |
| PRIORITIZE_SELF | รักษาตัวเองไว้ก่อน | HP/Strain เสี่ยงสูง |
| OBEY_GUIDANCE | เลือกสอดคล้องคำชี้นำ | มี Guidance จริง |
| PROTECT_TRUSTED | ปกป้องบุคคลที่ไว้ใจ | Trust มีผลหลัง implement |
| ITEM_SPENT | จี้ใช้หมดสำหรับ encounter นี้ | ไม่เกิดผลซ้ำ |
| TARGET_INVALID | เป้าหมายไม่เข้าเงื่อนไข | ไม่มี revive Dead |
| CRYSTAL_UNSAFE | อุปกรณ์ไม่ปลอดภัย | มี warning ก่อนตัดสิน |
| USE_ORDINARY_AID | ใช้ผ้าพันแผล/ช่วยแบบธรรมดา | ทางเลือกไม่ต้องมีเวท |

Reason Code เป็นชื่อเชิงออกแบบ ยังไม่ใช่ identifier ที่ถูกเพิ่มลงโค้ดจริง

## 5.3 Test Scenarios

**S1**: Player ได้รับบาดเจ็บ, NPC ผู้ถือจี้ Compassion สูง, NPC อีกคนสบายดี → โอกาสช่วย Player มากขึ้น  
**S2**: Player ออกคำชี้นำ Attack, NPC เพื่อนล้มและ bleed-out ใกล้หมด → NPC มีเหตุผลใช้จี้แทน Attack  
**S3**: จี้เป็น Spent → NPC เลือกใช้การช่วยธรรมดาหรือถอย ห้ามใช้จี้ซ้ำ  
**S4**: ทุกคนปลอดภัย → ไม่มีการใช้จี้เพื่อ “รีบใช้ให้หมด”  
**S5**: NPC ผู้ถือจี้กำลังกลัว/HP ต่ำ → อาจไม่ช่วย แม้ผู้เล่นสั่ง ซึ่งต้องสื่อเหตุผลชัด  
**S6**: NPC สองคนต้องการความช่วยเหลือ → ลำดับความสำคัญต้องอ่านได้และไม่ล็อกตามเลขดัชนี actor

หลังทดสอบให้ผู้เล่นภายนอกอธิบาย “NPC ทำไมเลือกแบบนั้น” โดยไม่อ่านโค้ด — หากอธิบายไม่ได้แปลว่าความยุติธรรม/feedback ยังไม่ผ่าน

# 6. การออกแบบทรัพยากรพลังในอนาคต

ไม่จำเป็นต้องเรียก Mana แบบทั่วไป ควรมีค่าใช้งานเชิงระบบที่เข้าใจได้สองส่วน:

- **Resonance Strain** อยู่ที่ตัวผู้ใช้: ความเหนื่อยและความเสี่ยงสะสมจากการกระตุ้น
- **Material Stress/Integrity** อยู่ที่อุปกรณ์: ความร้อน รอยร้าว การเสื่อม และผลึกเสีย

**ข้อเสนอสูตรกึ่งแนวคิด [OPEN ไม่ใช้ balance จริง]:**

~~~text
strain_gain = base_intensity × duration_factor × instability_factor × proficiency_modifier
item_stress = exertion × material_quality_modifier
successful_effect = precondition_met AND item_ready AND risk_not_prohibited
~~~

ทุก modifier ต้องมีช่วงขั้นต่ำที่ปลอดภัยและสมดุลกับเทิร์น/เวลาต่อสู้ที่ตัดสินภายหลัง; จงอย่าเขียนสูตรนี้เป็นโค้ดจนกว่า game loop จะเสถียร

## 6.1 ข้อจำกัดทาง balance

1. เวทต้อง **ไม่ outperform อุปกรณ์ปกติทุกสถานการณ์**; มี domain ที่มันเก่งเฉพาะ
2. ความเสียหาย/ความช่วยเหลือมีเพดานที่สามารถ balance กับ HP และ Injury ได้
3. การใช้ทรัพยากรหนึ่งครั้งควรสร้าง decision tradeoff ที่ชัด
4. ไอเทมไม่ยกเลิกความยากของ Permadeath
5. AI ศัตรู/ฝ่ายเดียวกันต้องเข้าถึงกฎเดียวกันเมื่อใช้อุปกรณ์ชนิดเดียวกัน
6. ความเสี่ยงผลึกแตกไม่ใช่ RNG ไม่มีเหตุผล; มีระดับคำเตือนกับทางเลือกป้องกัน
7. อุปกรณ์บางชนิดอาจต้องหยุดคิดหรือเตรียม 1 เทิร์นเพื่อสร้างจังหวะ tactical

## 6.2 ตัวอย่าง progression โดยไม่เพิ่มคลาส Mage

หากใช้โล่ Echo Shield ป้องกันเพื่อนซ้ำในเหตุการณ์เสี่ยง ผู้ใช้พัฒนาความชำนาญป้องกันและอาจได้ชื่อบทบาท “ผู้พิทักษ์” ตามระบบ Class เดิม; ความชำนาญพ้องพลังอาจเป็น *subskill* ที่เรียนจากการฝึกจริง ไม่ใช่สายอาชีพล็อกแยก

การฝึกเฉย ๆ โดยไม่มีความเสี่ยงหรือผลการเรียนรู้ไม่ควรเป็นวิธีปั่นเลเวลตาม v0.1

# 7. UI, Accessibility และ feedback

## 7.1 รูปแบบข้อมูลบนหน้าจอ

- ชื่ออุปกรณ์ + บทบาทสั้น ๆ มากกว่า “เวท Lv.7”
- ใช้สัญลักษณ์ข้าง item/action ซึ่งชัดเจนแม้ภาพ pixel art
- สถานะ Ready / Spent / Warning อ่านได้จากข้อความและสี ไม่ใช้ **สีอย่างเดียว**
- Tooltip สั้น: “ช่วยชะลอการเสียเลือด / ใช้ได้ 1 ครั้ง / ไม่ชุบผู้ตาย” (ใน prototype)
- Combat Log แสดง “ใคร → ทำอะไร → ทำไม → เกิดผลใด” แยก Reason กับ Result
- feedback animation สั้น ไม่บัง actor/target และให้ interrupt/reduced-motion ได้ตามขั้น polish

# 8. ผสานเข้ากับระบบ Journey / Town / Quest

## 8.1 Journey

- พื้นที่ผิดธรรมชาติเป็นเหตุการณ์พิเศษที่เปลี่ยนการวางเส้นทาง ไม่ใช่ random ambush ทุกจุด
- เข็มทิศเศษดาวอาจให้ข้อมูลเพิ่มแต่ไม่เปิดเผยของที่ซ่อนทั้งหมด
- NPC สำรวจอาจตีความสัญญาณต่างกันตาม Perception/ประสบการณ์ และผู้เล่นตัดสินใจว่าจะเชื่อใคร
- กฎ fatigue จากใช้พลังใน Journey ต้องมีผลถึง Combat **หลังจาก** ระบบ resource persistence พร้อม

## 8.2 Town

- ศูนย์นักผจญภัยมีข่าวลือเรื่องเศษดาว/ข้อห้ามทางเส้นทาง
- ผู้ประเมิน/ช่างอาจเปิดเป็น NPC UI เชิงเรื่องเล่า ไม่ต้องมีเมืองเดินเสรี
- ราคายังไม่ล็อก เศรษฐกิจ baseline ยังเป็นอาวุธทั่วไป
- บางไอเทมเช่ายืมจากสมาคมได้เพื่อให้เกิด choice ระหว่างภารกิจ แต่ *การเช่าเป็นแนวคิด [LATER]* ไม่ต้องทำทันที

## 8.3 Quest

- เงื่อนไขจบเควสต้องไม่บังคับให้มีของพิเศษที่ผู้เล่นไม่สามารถรู้/หาได้
- อุปกรณ์พิเศษควรเป็นทางเลือกหนึ่งในการแก้ ไม่ใช่ “key” ลับที่ทำให้ softlock
- ตัวเลือกไม่ใช้พลังอาจนำไปสู่ผลคนละแบบที่ยังเล่นต่อได้
- สัญญาณโลกเก่าค่อย ๆ เผยเป็นเบาะแส ไม่ใช่ cinematic ข้อมูลมหาศาล

# 9. โครงสร้างข้อมูล Godot — แนวทางในอนาคต ไม่ใช่คำสั่งให้รีแฟกเตอร์ตอนนี้

เป้าหมายการเรียนรู้คือ **เข้าใจจริงและลงมือเอง** ตาม v0.4 ไม่ยื่นโค้ดก้อนใหญ่ให้คัดลอก

## 9.1 ระยะที่ 1: ทดลองในสคริปต์เดิม

เมื่อถึง MRE-1 เพิ่ม booleans/ints ชั่วคราวใน scene test แยก ไม่ผูกกับเกมเต็ม

ตัวอย่าง pseudo-logic เท่านั้น:

~~~text
if not equipped: show "ต้องสวมจี้"; return
if item_spent: show "จี้หมดกำลัง"; return
if target_is_dead: show "ช่วยผู้ตายไม่ได้"; return
if not target_needs_aid: show "ไม่จำเป็นต้องใช้"; return
apply_stabilization(target)
item_spent = true
show_combat_feedback()
~~~

ผู้พัฒนาต้องสร้าง input, state, การเรียกเมธอด, signal UI และ test ด้วยตนเองโดยรับคำแนะนำทีละขั้นตาม v0.4

## 9.2 ระยะที่ 2: แยกข้อมูลจากพฤติกรรม (หลังทำต้นแบบสำเร็จ)

อาจใช้ Godot Resource สำหรับ ItemDefinition, CrystalCondition; ใช้ combat actor state สำหรับ Strain/Equipment; แยก Action Resolver จาก UI และจาก NPC Decision Resolver

โครงสร้างข้อมูลเชิงแนวคิด:

| Object | เก็บอะไร | ห้ามปะปน |
|---|---|---|
| ResonanceItemData | effect, target rule, item cost | ไม่ตัดสิน AI |
| CrystalState | stress, integrity, warning level | ไม่ควบคุม UI ตรง |
| ActorState | hp, bleeding, proficiency, strain | ไม่รู้ฉาก Node2D |
| ActionContext | actor, target, event, guidance | ไม่เขียน save |
| ActionResult | outcome, reasons, costs, events | ไม่ถือข้อมูลอาวุธถาวร |
| CombatPresenter | sprite, log, sound, focus | ไม่คำนวณ damage/AI |
| NPCDecision | เลือก action และ reason | ไม่สั่ง player โดยตรง |

**ไม่เพิ่ม singleton manager จำนวนมากตั้งแต่เริ่ม**; แยกเมื่อมีเหตุผลจากความซับซ้อนจริง

## 9.3 Save และ compatibility [LATER]

เมื่อมีเซฟถาวร:
- ระบุ version ของ schema/item state
- save เฉพาะ state ที่จำเป็น: item id, integrity, stress/charges, owner, relevant flags
- โหลดเซฟเก่าที่ไม่มี resonance keys เป็นค่าเริ่มต้นอย่างปลอดภัย
- ความตาย/การสูญเสียอุปกรณ์ต้องทำตามกฎ inventory และ world progression เดิม
- ต้องมี test โหลดเซฟเก่าและ reset encounter

# 12. วิธีประเมินความสนุก: Playtest Protocol

### กลุ่มทดสอบ
- **รอบ A:** ผู้พัฒนาเล่น scenario 6 แบบเพื่อหาความผิดพลาดเชิง logic
- **รอบ B:** ผู้เล่นภายนอก 3–5 คนเป็น *เป้าทดลองเบื้องต้น ไม่ใช่ sample เชิงสถิติ*
- **รอบ C:** เปรียบเทียบ encounter ที่มีไอเทม vs ไม่มีไอเทม (difficulty และตัวละครเหมือนกัน)

### คำถามหลังเล่น
1. คุณเข้าใจไหมว่า NPC ตัดสินใจใช้อุปกรณ์เพราะอะไร?
2. คุณคาดเดาได้ไหมว่าจะเกิดอะไรเมื่อผลึกเริ่มเสี่ยง?
3. ถ้าคุณถูกปฏิเสธคำชี้นำ รู้สึกว่า NPC มีเหตุผลหรือถูกสุ่มลงโทษ?
4. อุปกรณ์สร้างทางเลือกน่าสนใจขึ้น หรือทำให้กดชนะง่ายขึ้นเฉย ๆ?
5. หากตาย คุณยอมรับผลหรือรู้สึกว่าเกมซ่อนข้อมูลสำคัญ?
6. เมื่อพบอุปกรณ์ครั้งแรก รู้สึกเป็นสิ่งพิเศษจริงไหม?

**Fail Conditions:** ผู้เล่นส่วนใหญ่คิดว่าเป็นเวทชุบฟรี, ไม่เข้าใจเหตุผล NPC, รู้สึกไอเทมต้องมีเพื่อชนะทุกไฟต์, หรือการใช้ทำให้ combat ยืด/เยิ่นเย้อโดยไม่มีทางเลือกเพิ่ม

# 13. แนวทางการเรียนรู้ Godot แบบทีละบท

ตาม v0.4 ให้ AI เป็นโค้ช/คู่พัฒนา และผู้พัฒนาลงมือจริง:

| บท | สิ่งที่ได้เรียน | สิ่งที่เห็นในเกม |
|---|---|---|
| A — State | bool, int, state transition | Ready → Spent |
| B — Input/Validation | guard clauses และป้องกันการกดผิด | ใช้ไม่ได้เมื่อเงื่อนไขไม่ครบ |
| C — Actor/Target | การอ้างอิง node/state ไม่ผูกกับ UI | เลือกผู้บาดเจ็บเป้าหมาย |
| D — Signals | สื่อสารผลการใช้กับ HUD | Log และ HP/status เปลี่ยน |
| E — Feedback | AnimationPlayer/Tween/Audio เบื้องต้น | จี้เรืองแสงสั้น ๆ |
| F — Decision | กฎ AI และ Reason Code | NPC ปฏิเสธหรือช่วย |
| G — Regression | ฉากทดสอบกรณีต่าง ๆ | Restart/Defeat ไม่บั๊ก |
| H — Refactor | data-driven Resource เมื่อถึงเวลา | เพิ่ม item ใหม่โดยไม่ copy-paste มาก |

**หนึ่ง session ทำเพียงหนึ่งบท**; ก่อนเขียนให้ผู้พัฒนาอธิบายสิ่งที่ตั้งใจทำ ทดลองรัน และบันทึก diff สั้น ๆ

## 13.1 ขอบเขตงานวาดเพื่อสร้างแรงกระตุ้น

อนุญาตให้วาด concept/item icon เพื่อกระตุ้นความอยากทำเกม แต่ไม่ทำ asset production จำนวนมากก่อนมี encounter ทดลองที่ใช้มันจริง

ตัวอย่าง session คู่กัน: เขียน state Ready/Spent → วาดไอคอนจี้ 16×16 หรือ 24×24 → เชื่อม UI → ทดลองเล่น; สิ่งนี้ไม่ใช่ “หลุดแผน” หากมีผลต่อแรงจูงใจและขอบเขตชัด
